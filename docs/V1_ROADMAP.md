# WhisperMd — Roadmap до v1.0

> Рабочий документ проекта.  
> Цель: зафиксировать scope v1.0, архитектурные решения, порядок разработки и критерии готовности, чтобы не терять договорённости в контексте.

## 1. Цель v1.0

WhisperMd v1.0 — полноценное локальное Windows-приложение для пакетной транскрибации лекций через `whisper.cpp`.

Главный сценарий:

1. Пользователь загружает одну или несколько аудиозаписей.
2. При необходимости меняет порядок файлов.
3. Выбирает способ формирования заметок.
4. При необходимости группирует несколько записей в одну лекцию/заметку.
5. Добавляет контекстный prompt.
6. Запускает транскрибацию.
7. Видит текущий этап, прогресс, время и состояние очереди.
8. Получает Markdown-заметки.
9. Позже может открыть созданные заметки через историю приложения.

Real-time транскрибация **не входит в v1.0**.

---

## 2. Scope v1.0

### Обязательно входит

- полноценный современный GUI;
- очередь нескольких аудиофайлов;
- drag & drop файлов;
- изменение порядка записей;
- удаление файлов из очереди;
- три режима формирования заметок:
  - каждая запись отдельно;
  - все записи в одну заметку;
  - пользовательские группы;
- объединение нескольких частей одной лекции в одну заметку;
- contextual prompt;
- живой прогресс транскрибации;
- отображение этапа обработки;
- прошедшее время;
- состояние каждого элемента очереди;
- отмена текущей обработки;
- безопасная обработка конфликтов имён Markdown-файлов;
- Markdown как основной пользовательский формат;
- история заметок;
- поиск по истории;
- настройки;
- локальная работа без облака;
- CPU/Vulkan backend с автоматическим fallback;
- установщик Windows;
- запуск установленного приложения без исходного репозитория.

### Не входит в v1.0

- real-time транскрибация;
- пауза транскрибации;
- облачная синхронизация;
- аккаунты;
- мобильная версия;
- автоматическое AI-конспектирование;
- переход на более тяжёлую модель без отдельного решения;
- сложная система плагинов;
- обязательный экспорт в TXT/SRT/JSON через GUI.

## 3. Базовые архитектурные решения

### 3.1 GUI

Текущий WinForms считается прототипом.

Новый основной GUI:

- WPF;
- .NET 8;
- Windows-only;
- архитектура с разделением UI, состояния приложения и backend-оркестрации.

Причина: v1 требует очереди, групп, истории, карточек, настроек, drag & drop и сложных состояний интерфейса.

### 3.2 Whisper backend

Единым источником логики запуска Whisper остаётся:

`transcribe.ps1`

GUI не должен самостоятельно дублировать:

- параметры запуска `whisper.cpp`;
- выбор CPU/Vulkan;
- fallback;
- подготовку WAV;
- обработку путей;
- техническую логику транскрибации.

GUI передаёт параметры скрипту явно.

### 3.3 Обмен backend ↔ GUI

Текущий разбор строки `Results:` из stdout считается временным.

Нужен машинно-читаемый поток событий, например:

```text
WHISPERMD_EVENT {"type":"stage","value":"preparing"}
WHISPERMD_EVENT {"type":"progress","value":42}
WHISPERMD_EVENT {"type":"result","path":"..."}
WHISPERMD_EVENT {"type":"error","message":"..."}
```

GUI должен читать stdout/stderr потоково.

### 3.4 Результаты

Основной пользовательский формат v1:

`Markdown (.md)`

TXT/SRT/JSON могут использоваться внутри pipeline, но не обязаны быть доступны пользователю.

Архитектура должна позволять позже добавить новые форматы экспорта.

### 3.5 Хранилище

Предварительное решение:

- Markdown-файлы остаются обычными файлами на диске;
- метаданные и история хранятся в SQLite.

SQLite может хранить:

- ID заметки;
- название;
- дату создания;
- путь к Markdown;
- исходные аудиофайлы;
- группы;
- статус;
- длительность;
- prompt;
- дополнительные метаданные.

## 4. Основные сущности приложения

Предварительный набор доменных сущностей:

### Recording

Один исходный аудиофайл.

Примерные поля:

- ID;
- путь;
- имя файла;
- длительность;
- позиция в очереди;
- статус;
- прогресс;
- группа.

### RecordingGroup

Группа записей, которые должны стать одной заметкой.

Пример:

- `lecture_01_part1.m4a`
- `lecture_01_part2.m4a`

→ одна заметка `Лекция 1.md`.

### TranscriptionJob

Один запуск транскрибации.

Содержит:

- набор Recording;
- порядок;
- режим объединения;
- группы;
- prompt;
- backend;
- язык;
- настройки;
- состояние выполнения.

### Note

Итоговая Markdown-заметка.

Содержит:

- название;
- Markdown;
- путь;
- дату;
- связанные Recording;
- prompt;
- метаданные.

### AppSettings

Настройки приложения.

---

## 5. Режимы формирования заметок

### Режим 1 — отдельные записи

Каждый файл:

`Recording → Note`

### Режим 2 — всё в одну заметку

Все выбранные записи объединяются в установленном пользователем порядке:

`Recording 1 + Recording 2 + ... → Note`

### Режим 3 — группы

Пользователь вручную создаёт группы.

Пример:

```text
Группа: Матан — Лекция 1
  part_01.m4a
  part_02.m4a

Группа: Матан — Лекция 2
  part_03.m4a
```

Результат:

```text
Матан — Лекция 1.md
Матан — Лекция 2.md
```

Порядок записей внутри группы имеет значение.

---

## 6. Contextual prompt

Prompt является необязательным полем.

Назначение:

- передавать Whisper терминологический контекст;
- улучшать распознавание названий;
- подсказывать предмет;
- подсказывать специальные термины;
- снижать вероятность неверного выбора между акустически похожими словами.

Пример:

```text
Математический анализ.
Числовые ряды, сходимость, признак Даламбера,
признак Коши, абсолютная и условная сходимость.
```

Prompt не является инструкцией для полноценного reasoning.

---

## 7. UX транскрибации

Для каждого файла должны отображаться состояния:

```text
Ожидает
Подготовка аудио
Транскрибация
Формирование результата
Готово
Ошибка
Отменено
```

Для активного файла:

- прогресс;
- текущий этап;
- прошедшее время;
- имя файла;
- при возможности оценка оставшегося времени.

Для всей задачи:

- текущий файл / общее число файлов;
- общий прогресс очереди;
- число готовых;
- число оставшихся;
- кнопка отмены.

Пауза в v1 не нужна.

---

## 8. Конфликты Markdown-файлов

Существующие `.md` никогда не перезаписываются молча.

При конфликте показывается диалог:

- заменить;
- сохранить копию;
- отменить.

Для пакетной обработки желательно:

- `Применить ко всем`.

# 9. Этапы разработки

## Этап 0 — зафиксировать исходное состояние

Перед изменениями:

- проверить текущую сборку;
- проверить короткий файл через CPU;
- проверить короткий файл через Vulkan;
- убедиться, что существующий pipeline действительно работает;
- сохранить текущий рабочий код как локальную точку возврата.

GitHub пока не считается актуальным источником истины.

### Готово, когда

Старый pipeline подтверждён рабочим и есть безопасная точка возврата.

---

## Этап 1 — новый WPF-каркас

Создать новый GUI-каркас.

Основные разделы:

- Транскрибация;
- История;
- Настройки.

Real-time пока отсутствует.

Сразу определить:

- дизайн-систему;
- размеры окна;
- навигацию;
- базовые компоненты;
- состояние темы;
- layout приложения.

### Готово, когда

Приложение запускается и визуально выглядит как основа будущего продукта, а не технический прототип.

---

## Этап 2 — экран транскрибации

Реализовать:

- выбор файлов;
- drag & drop;
- очередь;
- карточки записей;
- удаление;
- изменение порядка;
- режимы заметок;
- создание групп;
- переименование групп;
- перемещение файлов между группами;
- поле prompt;
- кнопка запуска.

Backend пока может быть подключён минимально.

### Готово, когда

Пользователь может полностью сформировать будущую задачу транскрибации ещё до запуска Whisper.

---

## Этап 3 — backend protocol

Переделать `transcribe.ps1` так, чтобы он выдавал стабильные машинные события.

Добавить:

- stage;
- progress;
- result;
- warning;
- error;
- backend selected;
- fallback event.

GUI:

- читает stdout/stderr в реальном времени;
- парсит только структурированные события;
- обычный технический лог хранит отдельно.

### Готово, когда

GUI больше не зависит от текстовых строк вроде `Results:`.

---

## Этап 4 — очередь выполнения

Реализовать `TranscriptionJob`.

Поведение:

1. брать следующий Recording;
2. готовить WAV;
3. запускать Whisper;
4. получать прогресс;
5. сохранять промежуточный результат;
6. переходить к следующему;
7. корректно обрабатывать ошибки.

Ошибка одного файла не должна обязательно уничтожать всю очередь.

### Готово, когда

Можно загрузить несколько файлов и оставить приложение последовательно их обработать.

---

## Этап 5 — прогресс и отмена

Реализовать:

- живой прогресс;
- текущий этап;
- общий прогресс;
- таймер;
- потоковый лог;
- отмену текущего процесса;
- корректное завершение FFmpeg / whisper-cli;
- корректную очистку временных ресурсов.

Исходные аудио никогда не удаляются.

Диагностический WAV при ошибке сохраняется.

### Готово, когда

Пользователь понимает, что происходит во время обработки, и может безопасно её остановить.

---

## Этап 6 — сборка Markdown-заметок

После транскрибации:

- получить текст каждой Recording;
- сохранить порядок;
- объединить записи согласно выбранному режиму;
- сформировать Markdown;
- запросить название заметки либо сформировать его автоматически;
- разрешить конфликт существующего файла;
- сохранить Note.

Для объединённых файлов желательно оставлять структурные разделители между частями.

### Готово, когда

Все три режима формирования заметок дают корректный Markdown.

---

## Этап 7 — история и SQLite

Добавить локальную БД.

Реализовать:

- сохранение Note;
- список истории;
- открытие заметки;
- поиск по названию;
- поиск по содержимому;
- сортировку по дате;
- связь заметки с исходными Recording.

### Готово, когда

После перезапуска приложения пользователь видит ранее созданные заметки и может их найти.

---

## Этап 8 — настройки

Основные настройки:

- язык;
- backend:
  - Auto;
  - Vulkan;
  - CPU;
- папка библиотеки;
- prompt по умолчанию;
- поведение при завершении;
- поведение при конфликте файлов.

Дополнительно / advanced:

- threads;
- путь к модели;
- диагностические параметры.

Модель `small` остаётся стандартной для v1.

### Готово, когда

Основные параметры больше не захардкожены в GUI.

---

## Этап 9 — UX-polish

Пройти все пользовательские сценарии.

Добавить:

- пустые состояния;
- понятные ошибки;
- confirmation dialogs;
- drag & drop feedback;
- клавиатурные действия;
- disabled states;
- tooltips там, где нужны;
- повтор транскрибации;
- открыть Markdown;
- открыть папку;
- обработку отсутствующих файлов.

### Готово, когда

Приложением можно пользоваться без знания его внутренней архитектуры.

---

## Этап 10 — установщик

Цель:

пользователь получает один installer EXE.

Установщик должен разместить:

- WhisperMd;
- .NET runtime либо self-contained приложение;
- `whisper.cpp`;
- CPU backend;
- Vulkan backend;
- FFmpeg;
- модель;
- необходимые библиотеки;
- стартовые настройки.

Установщик:

- предлагает выбрать папку;
- создаёт ярлык;
- после установки приложение запускается без репозитория и ручной настройки среды.

### Готово, когда

WhisperMd можно установить в чистую директорию Windows и сразу использовать.

---

## Этап 11 — release smoke-test

Обязательные сценарии:

1. один короткий файл — Vulkan;
2. один короткий файл — CPU;
3. fallback Vulkan → CPU;
4. несколько файлов в очереди;
5. каждая запись отдельно;
6. все записи в одну заметку;
7. две пользовательские группы;
8. изменение порядка;
9. prompt;
10. отмена;
11. ошибка одного файла;
12. конфликт существующего `.md`;
13. перезапуск приложения;
14. история сохраняется;
15. поиск работает;
16. установка в новую директорию;
17. запуск без исходного репозитория.

### Готово, когда

Все обязательные сценарии проходят без критических ошибок.

# 10. Технические принципы

На протяжении всей разработки соблюдать:

1. Не удалять исходные аудиофайлы.
2. Не уничтожать существующий Markdown без подтверждения.
3. При ошибке сохранять диагностические данные.
4. Не дублировать Whisper-логику в GUI.
5. `transcribe.ps1` остаётся единым orchestration layer.
6. GUI работает через явный контракт.
7. После каждого крупного этапа приложение должно оставаться запускаемым.
8. Изменения делать небольшими проверяемыми шагами.
9. Не усложнять v1 функционалом real-time.
10. Не менять `small` и текущую стратегию CPU/Vulkan без отдельной причины.
11. GitHub пока не считать источником истины.
12. Сначала довести локальную v1, затем приводить репозиторий в порядок.
